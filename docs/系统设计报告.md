## 1. 背景调研与研究意义

### 1.1 研究背景

柔性作业车间调度问题（Flexible Job Shop Scheduling Problem, FJSP）是经典作业车间调度问题（JSP）的扩展，其核心特征在于每道工序可在多台机器中选择加工，从而更贴近实际制造场景。在离散制造业中，车间调度直接影响设备利用率、订单交付周期和生产成本，是生产管理的核心环节。

随着智能制造技术的发展，传统依赖人工经验的调度方式面临以下挑战：

1. **问题规模增大**：多品种、小批量生产模式下，调度问题的组合复杂度呈指数增长
2. **约束条件增多**：除机器约束外，还需考虑工装（Fixture）、交货期、优先级等多重约束
3. **决策透明度不足**：传统调度系统给出方案但缺乏解释，管理人员难以信任和调整
4. **人机协同需求**：调度人员需要与系统进行自然交互，而非面对复杂的参数配置界面

人工智能技术，特别是大语言模型（LLM）和智能体（Agent）技术的快速发展，为解决上述问题提供了新的思路。将AI Agent与调度算法结合，实现"自然语言指令→智能调度→结果解释"的完整链路，是智能制造中人机协同的重要发展方向。

### 1.2 研究意义

#### 1.2.1 理论意义

本研究探索大语言模型智能体与柔性作业车间调度系统的融合路径，验证AI Agent在复杂制造调度场景中的适用性。具体包括：

- 验证基于Agent的调度辅助模式在FJSP问题上的可行性
- 探索调度决策的自然语言可解释性方法
- 为AI Agent在智能制造领域的应用研究提供可复现的案例参考

#### 1.2.2 实践意义

柔性作业车间调度比传统JSP更贴近实际生产（每道工序可在多台设备中选择），但传统调度系统存在交互不直观、决策过程不透明等局限。本课题的实践价值在于：

1. **降低使用门槛**：通过自然语言交互和可视化界面，使非专业人员也能使用调度系统
2. **提升决策透明度**：不仅给出调度方案，还提供关键路径、负载均衡等决策依据的自然语言解释
3. **支持快速验证**：基于公开基准数据集，调度结果可复现、可对比
4. **轻量部署**：纯Python后端+CDN前端，无需复杂环境配置即可运行

### 1.3 国内外研究现状

#### 1.3.1 FJSP求解方法

FJSP是NP-hard问题，现有求解方法主要分为三类：

1. **精确算法**：分支定界法、动态规划等，仅适用于小规模问题
2. **启发式算法**：优先调度规则（SPT、LPT、EDD等），求解速度快但解的质量有限
3. **元启发式算法**：遗传算法（GA）、模拟退火（SA）、蚁群算法（ACO）、粒子群优化（PSO）等，在解的质量和计算效率之间取得较好平衡

其中遗传算法因其全局搜索能力强、易于处理多重约束，成为FJSP领域应用最广泛的算法之一。

#### 1.3.2 AI在调度中的应用

近年来，AI技术在调度领域的应用主要体现在：

1. **强化学习调度**：将调度问题建模为马尔可夫决策过程，通过智能体学习调度策略
2. **大模型辅助调度**：利用LLM的推理和自然语言能力，辅助调度参数配置和结果解释
3. **混合智能系统**：将优化算法与AI推理结合，兼顾求解质量和决策可解释性

本项目采用"遗传算法求解+AI辅助交互与解释"的混合模式，在保证求解质量的同时提升系统的易用性和透明度。

### 2.2 方案论证

#### 2.2.2 调度算法选型

| 算法 | 优点 | 缺点 | 适用性 |
|------|------|------|--------|
| **遗传算法（选定）** | 全局搜索能力强，适合FJSP，易于处理多重约束 | 参数调优复杂 | 柔性作业车间调度 |

| 强化学习 | 可在线学习 | 训练周期长，需大量数据 | 有充足历史数据 |

**选型结论**：主选自研遗传算法，采用POX交叉保序、锦标赛选择、精英保留策略，确保求解质量和可解释性。

#### 2.2.3 前端技术选型

| 对比项 | Vue3+CDN（选定） | React | 原生JS |

## 3. 数据资源构建

### 3.1 数据集来源

本项目使用 **FJSP-F（含工装约束的柔性作业车间调度数据集）** 作为算法验证与系统测试的基准数据。

| 项目 | 内容 |
|------|------|
| 数据集名称 | FJSP-F benchmark |
| 发布机构 | 华中科技大学 |
| 数据来源 | https://zenodo.org/records/11526695 |
| 实例数量 | 20个（FJSP-F1 至 FJSP-F20） |
| 规模范围 | 3作业×2机器×2工装 至 20作业×10机器×12工装 |
| 原始格式 | `.mat`（MATLAB格式） |
| 预处理格式 | `.json`（结构化JSON） |
| 数据集类型 | 公开基准数据集（非自建） |

该数据集是FJSP领域广泛使用的标准测试集，其特点在于每个工序可在多台机器中选择，且包含工装（Fixture）约束，比传统JSP更贴近实际生产场景。

### 3.2 原始数据格式与变量说明

`.mat` 文件中包含以下主要变量：

| 变量名 | 含义 |
|--------|------|
| `dt` | 每个作业的交货期（delivery time） |
| `Jm` | 每道工序的可选机器集合（eligible machine set） |
| `JmNumber` | 机器总数 |
| `Jf` | 每道工序的可选工装集合（eligible fixture set） |
| `pjob` | 每个作业的优先级（priority） |
| `rt` | 每个作业的释放时间（release time） |
| `T` | 每道工序在各可选机器上的加工时间（processing time） |
| `fixnumbegin` | 各类工装的初始库存数量 |
| `fixnumend` | 生产后各类工装的数量 |
| `fixtype1` / `fixtype2` | I型/II型工装类别 |
| `machineF` | 机器与工装的对应关系 |
| `LB` | 下界（lower bound） |

### 3.3 数据预处理流程

由于系统应用控制策略阻止numpy和scipy的原生DLL加载，无法使用`scipy.io.loadmat`读取.mat文件。为此，项目采用纯Python方案完成数据预处理，流程如下：

#### 3.3.1 纯Python .mat解析器

编写`data/scripts/mat_reader.py`，仅使用Python标准库（struct + zlib）解析MATLAB 5.0格式的.mat文件，支持：
- 压缩数据元素（miCOMPRESSED）
- 元胞数组（miCELL）
- 小数据元素格式（Small Data Element）
- 无8字节对齐的特殊格式

#### 3.3.2 数据提取与结构化

编写`data/scripts/preprocess.py`，完成以下处理：

1. **解析**：调用mat_reader读取每个.mat文件
2. **提取**：从原始变量中提取作业、机器、工装、工序、加工时间、交货期、释放时间、优先级等信息
3. **清洗与补全**：对于解析不完整的字段，根据实例规模和FJSP问题特征自动补全合理数据（如每道工序可选2-4台机器、加工时间5-50、工装1-3种），使用固定随机种子（`42 + 实例编号`）保证可复现
4. **结构化**：转换为统一的JSON格式，包含scale、jobs、machines、fixtures、metadata五大模块
5. **索引生成**：生成`index.json`汇总所有实例的规模信息

#### 3.3.3 数据验证

编写`data/scripts/verify.py`，对所有20个实例进行完整性验证：
- 无空字段
- 作业数、机器数、工装数与scale一致
- 每道工序的可选机器数与加工时间数一致
- 加工时间为正数
- 数据规模在合理范围内

## 4. 系统概述

### 4.1 设计目标

本系统旨在构建一个 B/S 架构的柔性作业车间智能调度辅助平台，核心目标包括：

1. **智能求解**：基于遗传算法自动求解含工装约束的 FJSP 调度问题
2. **可视交互**：提供甘特图、收敛曲线、数字孪生等多维度可视化
3. **数据驱动**：集成工业大数据分析，支持瓶颈识别与多实例对比
4. **决策透明**：以自然语言解释调度决策，辅助管理人员理解方案
5. **轻量易用**：纯Python后端 + CDN前端，无需复杂部署即可运行

### 4.2 设计原则

| 原则 | 说明 |
|------|------|
| 模块化 | 算法、数据、API、前端各层独立，低耦合高内聚 |
| 纯Python | 后端不依赖含原生DLL的库，确保在受限环境可运行 |
| 可测试 | 核心模块均有自动化单元测试 |
| 可扩展 | 算法可替换、数据源可扩展、前端组件可复用 |
| 用户友好 | 操作流程简洁，错误提示明确，加载状态可见 |

└──────────────────────────┬──────────────────────────────┘
                           │ HTTP/RESTful API (JSON)
┌──────────────────────────▼──────────────────────────────┐
│                     业务逻辑层（后端）                       │
│  Flask Web框架                                              │
│  ┌────────────┐ ┌────────────┐ ┌──────────────────────┐ │
│  │  调度算法模块 │ │ 数据分析模块 │ │    API路由层         │ │
│  │  (GA求解器)  │ │ (统计/瓶颈) │ │ (请求处理/参数校验)  │ │

### 5.2 技术选型

## 8. 遗传算法设计

### 8.1 算法概述

本系统采用遗传算法（Genetic Algorithm, GA）求解含工装约束的柔性作业车间调度问题。算法核心是通过模拟自然选择与遗传进化，在解空间中搜索近优调度方案。

### 8.2 编码方案

采用**两段式染色体编码**：

#### 8.2.1 操作序列段（OS）

- 每个作业号 `j` 在序列中出现 `n_j` 次（`n_j` 为作业j的工序数）
- 第 k 次出现的作业号 j 表示作业 j 的第 k 道工序
- 序列长度 = 总工序数 Σn_j
- 示例（3作业，每作业3工序）：`[1, 2, 1, 3, 2, 3, 1, 2, 3]`

#### 8.2.2 机器分配段（MA）

- 每个元素为对应工序分配的机器编号
- 长度 = 总工序数
- 机器编号必须在该工序的可选机器集合中
- 示例：`[1, 2, 1, 2, 1, 2, 1, 2, 1]`

### 8.3 解码算法

采用**主动调度解码（Active Schedule Decoding）**：

```
输入：操作序列OS，机器分配MA
输出：机器调度表，作业调度表，Makespan

1. 初始化：
   - machine_available_time[m] = 0  (每台机器的可用时间)
   - job_next_op[j] = 0  (每个作业的下一道工序索引)
   - fixture_available_time[f] = 0  (每套工装的可用时间)

2. 遍历操作序列中的每个作业号j：
   a. op_idx = job_next_op[j]，获取工序详情
   b. machine = MA中对应位置的机器编号
   c. processing_time = 该工序在machine上的加工时间
   d. fixture = 选择可用的工装（eligible_fixtures中最早可用的）
   e. start_time = max(machine_available_time[machine],
                        job_last_finish_time[j],
                        fixture_available_time[fixture])
   f. end_time = start_time + processing_time
   g. 更新：machine_available_time[machine] = end_time
            job_last_finish_time[j] = end_time
            fixture_available_time[fixture] = end_time
   h. 记录调度信息到机器调度表和作业调度表
   i. job_next_op[j] += 1

3. Makespan = max(job_last_finish_time)
```

### 8.4 适应度函数

```
fitness(chromosome) = 1 / Makespan(chromosome)
```

Makespan 越小，适应度越高。

### 8.5 遗传操作

#### 8.5.1 选择操作

采用**锦标赛选择（Tournament Selection）**：
- 锦标赛大小 k = 3
- 从种群中随机选取 k 个个体，选择适应度最高的作为父代
- 重复直到选满种群大小

#### 8.5.2 交叉操作

**操作序列段**：采用 **POX（Precedence Operation Crossover）交叉**

```
1. 将作业集随机分为两个非空子集 J1 和 J2
2. 子代1：
   - 从父代1复制J1中作业的所有出现位置（保持原顺序）
   - 从父代2复制J2中作业的所有出现位置（按父代2顺序填入空位）
3. 子代2：
   - 从父代2复制J1中作业的所有出现位置
   - 从父代1复制J2中作业的所有出现位置
```

POX交叉的优势：保持每个作业内部工序的先后顺序，生成的子代始终是合法调度。

**机器分配段**：采用**均匀交叉（Uniform Crossover）**
- 每个位置以50%概率从父代1继承，50%从父代2继承
- 交叉后校验机器合法性，不合法则随机重选

#### 8.5.3 变异操作

**操作序列段**：**交换变异（Swap Mutation）**
- 随机选择两个位置，交换其元素
- 变异概率 Pm = 0.1

**机器分配段**：**随机重选变异**
- 随机选择一个位置，从该工序的可选机器中随机选择另一台
- 变异概率 Pm = 0.1

#### 8.5.4 精英保留

- 每代保留当前最优个体（Elite）直接进入下一代
- 精英数量 = 1
- 确保最优解不会因交叉变异而丢失

### 8.6 算法流程

```
开始
  │
  ▼
初始化种群（随机生成 pop_size 个染色体）
  │
  ▼
评估种群（解码每个染色体，计算Makespan和适应度）
  │
  ▼
记录最优个体，记录收敛数据
  │
  ▼
┌─→ 达到最大迭代代数？──是──→ 输出最优解，结束
│        │
│        否
│        ▼
│   选择（锦标赛选择）
│        │
│        ▼
│   交叉（POX + 均匀交叉）
│        │
│        ▼
│   变异（交换 + 随机重选）
│        │
│        ▼
│   精英保留（最优个体直接进入下一代）
│        │
│        ▼
│   评估新种群
│        │
│        ▼
└─── 更新最优个体，记录收敛数据
```

## 12. 关键技术难点与解决方案

### 12.1 原生库DLL加载被阻止

**问题**：系统应用控制策略阻止 numpy、pydantic_core 等含原生DLL的库加载，导致 FastAPI、numpy 等常用库无法使用。

**解决方案**：
1. 后端框架从 FastAPI 改为纯 Python 的 Flask
2. 遗传算法全部使用 Python 原生 list/dict 实现，不依赖 numpy
3. 数据统计使用 Python 内置 math 模块计算均值、标准差
4. JSON 序列化/反序列化使用 Python 内置 json 模块

### 12.2 MATLAB .mat 文件解析

**问题**：FJSP-F 数据集为 MATLAB .mat 格式，scipy.io.loadmat 依赖 numpy 无法使用；.mat 格式复杂（含压缩元素、小数据元素、无8字节填充等特殊格式）。

**解决方案**：
1. 编写纯 Python .mat 解析器（`data/scripts/mat_reader.py`），仅使用 struct + zlib
2. 逐步调试，识别该数据集的特殊格式特征
3. 对解析不完整的字段，按 FJSP 特征 + 固定种子补全合理值（用户明确指示）

### 12.3 Git HTTPS传输失败

**问题**：Git HTTPS 传输依赖的 libcurl-4.dll 被系统应用控制策略阻止加载，重装无效。

**解决方案**：
1. 改用 SSH 协议，使用 Windows 自带 OpenSSH 生成 ed25519 密钥
2. 22端口被网络拒绝，配置 `~/.ssh/config` 走 `ssh.github.com:443`
3. 成功推送所有提交

### 12.4 遗传算法编码与解码

**问题**：FJSP 的染色体编码需要同时表示工序优先级和机器分配，解码时需满足工艺约束、机器约束、工装约束。

**解决方案**：
1. 采用两段式编码（操作序列 + 机器分配）
2. 操作序列使用基于作业号的编码，天然满足工序先后约束
3. POX交叉保序，确保子代始终合法
4. 解码时同时跟踪机器可用时间、作业上道工序完成时间、工装可用时间，取最大值作为开始时间

### 14.2 关键prompt策略

#### 14.2.1 提示词工程

在与AI交流时，采用结构化的提示词方法：

1. **任务拆解**：将复杂任务分解为可独立执行的子任务（如"先实现GA编码，再实现解码，最后实现交叉变异"）
2. **约束说明**：明确技术约束（如"必须使用纯Python，不能依赖numpy"、"编码采用两段式"）
3. **验收标准**：给出明确的验收条件（如"28项测试全部通过"、"FJSP-F1的Makespan≤30"）
4. **上下文提供**：提供相关代码片段、数据结构定义、错误信息等上下文

#### 14.2.2 上下文工程

1. **项目规则文件**：在项目根目录维护AGENTS.md等规则文件，让AI先了解项目规范再修改代码
2. **先读代码再改**：要求AI在修改任何文件前先完整读取相关文件，避免基于印象修改
3. **渐进式修改**：每次只修改一个功能点，修改后立即验证，避免大面积改动引入难以定位的问题

#### 14.2.3 规格驱动开发

遵循"需求文档→AI制定计划→分步实现→逐步验收"的流程：

1. 先撰写需求规格说明书，明确功能需求和验收标准
2. 让AI根据需求制定实现计划
3. 按计划分步实现，每步完成后运行自动化测试验证
4. 全部完成后进行集成测试和端到端验证

#### 14.2.4 自动化测试与人工审查

1. **自动化测试**：为核心模块（算法、数据库、分析、API）编写单元测试和集成测试，共4个测试套件28项测试
2. **人工审查**：对AI生成的关键代码（如遗传算法的交叉变异逻辑、解码算法）进行人工审查，确保逻辑正确
3. **调试与人工接管**：当AI生成的代码出现问题时，采用回滚、缩小改动范围、最小复现等策略定位问题，必要时人工接管修改

### 14.3 AI出错案例及纠正过程

本项目开发过程中遇到多个AI生成代码或方案的问题，以下是典型案例及纠正过程：

#### 案例1：原生库DLL加载被阻止

**问题**：AI最初建议使用FastAPI + numpy + scipy技术栈，但系统应用控制策略阻止pydantic_core、numpy等含原生DLL的库加载，导致ImportError。

**纠正过程**：
1. 识别错误根因：DLL load failed: 应用程序控制策略已阻止此文件
2. 放弃FastAPI，改用纯Python的Flask框架
3. 遗传算法全部使用Python原生list/dict实现，不依赖numpy
4. 数据统计使用Python内置math模块计算均值、标准差
5. 编写纯Python .mat解析器替代scipy.io.loadmat

#### 案例2：MATLAB .mat文件解析失败

**问题**：AI最初建议使用scipy.io.loadmat读取.mat文件，但scipy不可用。AI随后生成的纯Python解析器无法正确处理该数据集的特殊格式（压缩元素、小数据元素、无8字节填充）。

**纠正过程**：
1. 逐步调试，对比解析结果与MATLAB中读取的结果
2. 识别该数据集使用MATLAB 5.0格式的特殊变体
3. 修复压缩数据元素的解压逻辑
4. 修复小数据元素格式（Small Data Element）的解析
5. 处理无8字节对齐的特殊情况
6. 对解析不完整的字段，按FJSP问题特征+固定种子补全合理值（用户明确指示"不要硬解析"）

#### 案例3：Git HTTPS传输失败

**问题**：AI建议使用标准的Git HTTPS方式推送，但Git依赖的libcurl-4.dll被系统应用控制策略阻止加载，重装Git无效。

**纠正过程**：
1. 识别错误：unable to access ...: failed to load libcurl-4.dll
2. 放弃HTTPS，改用SSH协议
3. 使用Windows自带OpenSSH生成ed25519密钥
4. 发现22端口被网络拒绝，配置~/.ssh/config走ssh.github.com:443
5. 成功推送所有提交

#### 案例4：subprocess.Popen title参数崩溃

**问题**：AI生成的启动脚本使用subprocess.Popen(..., title="FJSP Backend")，但Popen不支持title参数（仅subprocess.run支持），导致TypeError立即崩溃，启动脚本显示"System stopped."。

**纠正过程**：
1. 直接运行start.py捕获完整错误信息
2. 定位到Popen的title参数不被支持
3. 移除title参数，改用CREATE_NEW_CONSOLE让子进程在独立窗口运行
4. 后续发现CREATE_NEW_CONSOLE在部分环境仍有兼容性问题，最终改用纯bat的start命令实现窗口管理

#### 案例5：ECharts甘特图空白

**问题**：AI生成的甘特图代码使用echarts.graphic.clipRectByRect进行矩形裁剪，但该函数在某些情况下返回null，导致甘特图渲染为空白。

**纠正过程**：
1. 在浏览器控制台查看ECharts报错
2. 定位到clipRectByRect返回null
3. 移除裁剪函数，改用直接矩形渲染
4. 添加nextTick延迟和图表dispose清理，避免实例冲突
5. 添加全链路console.error日志，便于后续排查

#### 案例6：启动脚本双击闪退（Microsoft Store Python占位符）

**问题**：用户双击启动系统.bat时显示"Failed to install dependencies"，原因是系统PATH中WindowsApps的python.exe（微软商店占位符，非真实Python）被优先找到，导致flask安装失败。

**纠正过程**：
1. 检查系统中所有Python安装，发现唯一真实Python在Doubao沙箱运行时目录
2. 重写bat的Python检测逻辑：三级搜索策略
   - 优先搜索Doubao沙箱运行时Python目录
   - 遍历where python结果，跳过含WindowsApps的路径
   - 搜索常见安装路径
3. 每个候选Python都用-c "print(1)"验证可真正运行
4. pip安装依次尝试USTC→清华→官方三个镜像源
5. 模拟WindowsApps在PATH最前的环境实测通过

6. **自动化测试**：4个测试套件28项测试（GA 5项+数据库5项+分析6项+API 12项）全部通过
7. **文档齐全**：需求规格说明书（11000字）、系统设计报告（本文档）、README、API文档、数据说明
8. **工程工具**：一键启动/关闭脚本，支持双击运行，自动检测Python环境和依赖

系统在受限环境（系统应用控制策略阻止原生DLL加载）下仍能完整运行，体现了良好的工程适应性。项目全程使用Git管理，小步提交，保留完整的提交历史和AI交流记录。

### 16.2 不足与局限

1. **算法单一**：目前仅实现了遗传算法，未实现多种算法的对比和自动选择
2. **多目标优化不足**：当前仅以Makespan为优化目标，未考虑成本、能耗等多目标
3. **数字孪生简化**：数字孪生页面为二维简化模型，未实现三维可视化
4. **实时调度缺失**：当前为静态调度，未支持动态事件（如设备故障、紧急插单）下的重调度
5. **大模型集成有限**：当前系统的"AI辅助"主要体现在开发过程和决策解释文本生成，未实现大模型的实时推理交互

### 16.3 未来展望

后续可从以下方向扩展和改进：

1. **多算法融合**：增加模拟退火、蚁群算法、强化学习等多种调度算法，实现算法自动选择和混合优化
2. **多目标优化**：将优化目标从单一Makespan扩展为工期+成本+能耗的多目标优化，使用Pareto前沿方法
3. **实时调度与重调度**：支持动态事件（设备故障、紧急插单、加工时间波动）下的实时重调度
4. **数字孪生增强**：引入Three.js实现三维车间可视化，支持设备模型导入和实时状态映射
5. **大模型深度集成**：接入大语言模型API，实现自然语言指令解析、调度参数智能推荐、调度方案对话式调整
6. **MES系统集成**：通过OPC UA或RESTful API与MES/ERP系统对接，实现真实生产数据的实时获取和调度指令下达
7. **部署优化**：支持Docker容器化部署，提供云端部署方案，支持多用户并发访问
